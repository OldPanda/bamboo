They are observations, not guarantees, medians, or comparisons with Parqlab. The million-row file is only about 4.93 MiB and compresses very well.

The cancellation test interrupted a running trillion-pair aggregate in approximately **0.114 ms** after issuing cancel, then successfully ran another query. A separate 10 ms parent deadline test also passed. These are test observations, not general cancellation latency promises. Process RSS and cold-disk performance were not measured; the 256 MB setting is DuckDB's buffer/engine budget, not a hard total-memory bound.

## Workflow reference

[Parqlab's public product page](https://parqlab.app/) was reviewed for the local-exploration workflow. Bamboo implements direct open → visible rows → filter/sort → schema → SQL → explicit result export. It has its own UI and implementation. Cloud/data-lake features, dashboards, multi-file projects, and full-result multi-format exports were intentionally outside this first version. No proprietary benchmark was reproduced, and no comparative speed claim is made.

## Remaining acceptance checks

Native UI automation via System Events did not complete on this host and was stopped. The native picker/save APIs and file-drop wiring compile and are present, but the following need a human desktop pass:

1. Open a file through the native picker; cancel that picker and confirm the previous file remains.
2. Drop a `.parquet` file from Finder, then drop malformed input and confirm recovery.
3. Export through the native save dialog, inspect the JSON, cancel export, and try an existing filename (must refuse overwrite).
4. Confirm keyboard shortcuts, text selection/copy, screen-reader output, and normal quit behavior with the native desktop UI.

Further untested scope: multi-GB real-world files, compressed pathological/hostile files, encrypted Parquet, full process memory-pressure behavior, Intel Macs, Windows/Linux, signing/notarization for distribution. No claim is made that this first version handles all of those.
